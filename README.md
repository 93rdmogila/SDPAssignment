# Pattern Builder: Character Creation System

Учебный проект на Java 17+, демонстрирующий реализацию порождающего шаблона проектирования **Builder (Строитель)** с соблюдением принципов Clean Code, SOLID и современных возможностей языка (`record`, `enum`, Fluent API).

---

## 📌 Архитектура и структура проекта

Проект состоит из 6 модулей, расположенных в отдельных файлах:

* **`Role.java`** (`enum`) — перечисление ролей персонажей (`WARRIOR`, `MAGICIAN`) с поддержкой отображаемых текстовых названий (Type Safety).
* **`Character.java`** (`record`) — продукт сборки. Неизменяемый (immutable) контейнер данных с переопределённым `toString()`.
* **`CharacterBuilder.java`** (`interface`) — интерфейс строителя, задающий контракт для пошаговой настройки и сборки объекта.
* **`WarriorBuilder.java` / `MagicianBuilder.java**` (`class`) — конкретные строители с Fluent API, значениями по умолчанию и двухуровневой валидацией.
* **`CharacterDirector.java`** (`class`) — директор, управляющий процессами создания типовых персонажей по готовым рецептам.
* **`Main.java`** (`class`) — точка входа, демонстирующая сборку объектов и обработку исключений.

---

## 🛠 Валидация и правила бизнес-логики

В проекте чётко разделены два типа ошибок:

1. **`IllegalArgumentException`** — выбрасывается сразу в сеттерах при передаче некорректных аргументов (`hp <= 0`, пустые строки `name` или `weapon`).
2. **`IllegalStateException`** — выбрасывается в методе `build()` при нарушении правил комбинации полей класса:
* **Воин:** `HP >= 100`, `Mana <= 20`, запрет на использование маговского оружия (`посох`, `палочка`).
* **Маг:** `HP <= 100`, `Mana >= 50`, запрет на использование тяжёлого физического оружия (`меч`, `топор`).

## 💡 Соответствие принципам SOLID

* **Single Responsibility Principle (SRP):** `Character` только хранит данные, `Builder` отвечает за валидацию и сборку, `Director` хранит пресеты.
* **Open/Closed Principle (OCP):** Для добавления нового класса (например, `ArcherBuilder`) не требуется менять существующие классы или интерфейсы.
* **Liskov Substitution Principle (LSP):** Любой строитель заменяем через интерфейс `CharacterBuilder`.
* **Interface Segregation Principle (ISP):** Интерфейс строителя содержит только необходимые для сборки методы.
* **Dependency Inversion Principle (DIP):** Директор зависит от абстракции `CharacterBuilder`, а не от конкретных реализаций.
